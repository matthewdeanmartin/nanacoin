# Captured OOM at the 256-to-257 transaction boundary

Follow-up: [the ledger experiment](LEDGER-EXPERIMENT-2026-09-18.md) reproduced
this on a fresh board and identified the failing transaction-slice growth.

Tested the existing flashed board at `192.168.1.158`, with native USB serial
captured alongside HTTP. No firmware was changed or flashed. Firmware build
identity is unknown; the local source/runtime inspection below is supporting
evidence, not a verified binary-to-source mapping.

The household was already populated: four users, six active listings and 235
transactions. The user authorized a disposable household. This is an aged-heap
reproduction, not a fresh-boot capacity measurement.

## Observed

1. 100 status requests passed in `runs/initial-status`.
2. 250 requests each to status, me, ledger (`limit=30`) and listings passed in
   `runs/read-isolation`: 1,000 load requests, no unexpected status or timeout.
   Minimum pre-handler free bytes were 36,112 / 36,880 / 36,464 / 38,192.
   Transaction count stayed 235; the ledger balance check stayed true.
3. 60 issuance requests with one repeated idempotency key all returned 201.
   Transaction count increased only once, from 235 to 236.
4. New-key issuance then completed 20 times, taking the inferred count to 256.
   The 21st request received no HTTP response headers. Serial printed an OOM
   at **2026-09-18 15:33:25.550 UTC**, 30.781 seconds into `write-isolation`.

The final serial sequence was:

```text
heap conn 7751 refused 262: free 39376 inuse 242768 delta 35584 obj 618 blk/100 1227 mallocs 935621 frees 935003 gc 7998
heap conn 7752 refused 262: free 39312 inuse 242832 delta 35648 obj 619 blk/100 1225 mallocs 935749 frees 935130 gc 7999
heap conn 7753 refused 262: free 39248 inuse 242896 delta 35712 obj 620 blk/100 1224 mallocs 935877 frees 935257 gc 8000
fatal error: out of memory
abort called
```

The last successful response header reported 37,808 bytes free. No additional
load requests were launched after the fatal message. The listing-churn phase
was never reached. Recovery results and the final board snapshots are in
`runs/write-isolation/summary.json` and `report.md`. All three recovery probes
failed; diagnostic and log endpoints also remained unreachable. The board was
left unreset after capture, with no additional workloads attempted.

The eight-KiB headroom guard did not fire: this crash occurred with substantial
reported aggregate free bytes. Increasing the frequency of total-free polling
alone would not have explained or predicted it.

## Leading explanation, still to verify

`internal/ledger/book.go` declares `txns []PackedTransaction` and `revBy
[]uint32`; its constructor does not reserve capacity. `Book.apply` appends to
both slices at lines 308–309. Packed records do not imply preallocated storage.

The installed TinyGo runtime at
`C:/Users/matth/scoop/apps/tinygo/current/src/runtime/slice.go` implements growth
as `newCap = 1 << bits.Len(uint(newCap))`, then allocates the new buffer and
copies the old one. A request for the 257th element therefore requires a new
512-element buffer. The old 256-element buffer remains needed during the copy.
The transaction slice is the much larger of the two growing buffers.

The exact boundary, healthy preceding writes, stable read runs and surviving
idempotency replay make ledger growth the priority suspect. The evidence does
**not** identify the exact failing allocation, the largest free run, or the
target's current packed-record size. Aggregate free memory cannot establish
whether a sufficiently large contiguous block existed. No inference from
`blk/100` is needed to identify the growth boundary.

## Next experiment before choosing a fix

After preserving the evidence and resetting/reprovisioning the disposable
board, repeat `issue-new` across transaction 257. Starting from zero, allow
at least 270 operations; starting from existing data, choose enough to cross
the next capacity boundary. The default run keeps each request's health and
all serial lines; newer traces also retain each returned transaction ID.

```powershell
python bottleneck.py --scenarios issue-new --operations 270 --allow-writes --provision --serial auto --seconds 600
```

If a fresh heap passes 257, repeat after read/auth/listing churn, keeping the
same final transaction boundary. Passing on a fresh heap would distinguish
heap history from a hard total-capacity limit; it would not invalidate this
captured OOM. Repeat with monitoring disabled to measure its contribution.

For decisive allocation-site confirmation, add **diagnostic-only** serial
markers immediately before/after ledger slice growth, including `len`, `cap`,
target `unsafe.Sizeof(PackedTransaction{})` and requested new buffer bytes.
Avoid heap-allocating formatting. If possible, expose allocator largest-free-run
and failed-request size too. Capture those before optimizing or changing
capacity. These firmware instrumentation changes have not been made here.

The earlier HTTP/scratch/unpacking/idempotency optimization candidates remain
in `EXPERIMENTS.md`. Ledger backing-slice growth now precedes them in priority.
